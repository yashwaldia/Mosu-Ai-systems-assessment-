              Source of Truth

Controls whether an action is approved (approvedActionId === pendingAction.id), how many attempts have run (delivery.attempts), and whether delivery is not_sent, unknown, or sent.

              Zero Authority

              D. Historical Memory vs. Active Authorization
              Audit Only
            

            

              Prior versions (e.g., profile-017 v3 approved earlier) are retained in historical audit memory so the designer can compare changes, but never grant permission to v4 or authorize new outgoing actions.
            

          

        


        
        

          

            
Question: What happens if the profile or protocol changes after an action is approved, before it is sent?

            

              This is a classic Time-of-Check to Time-of-Use (TOCTOU) race condition. If a designer approves a clarification for v4 under protocol r1, and either the customer submits v5 or the designer updates the protocol to r2 before SEND executes, sending the old message would be misleading.
            

          


          

            
Deterministic Safety Mechanism (Implemented in Scenario C)

            
    
              
  1. Content-Addressed Action Identity (makeActionId): The action ID SHA-256 hashes the tuple [kind, profileId, profileVersion, recipient, text, protocolRevision].
    2. 
              
  2. Automatic Approval Invalidation on Reload: When LOAD_PROFILE runs after a profile or protocol revision change, the recomputed action.id changes. Because previous.pendingAction.id !== action.id, state.approvedActionId is deterministically reset to null and attempts resets to 0.
    3. 
              
  3. Pre-Send Freshness Guard in SEND: Before calling tools.notify, the harness/workflow verifies that state.approvedActionId === state.pendingAction.id and that the active protocol.revision matches the action's bound revision. If stale, SEND is blocked (0 calls) until the designer approves the newly regenerated clarification.
    4. 
            

            

              
            

          

        


        
        

          

            
1. Where the Loop Begins & Ends (Bounded Retry Loop)

            

              The retry loop begins when SEND catches a TIMEOUT from tools.notify, transitioning delivery.status to 'unknown'. Another attempt is permitted only while delivery.status !== 'sent' and delivery.attempts < MAX_ATTEMPTS (2). The loop terminates deterministically either when a receipt is recovered (status = 'sent') or at 2 uncertain attempts (outcome = 'needs_reconciliation'), escalating to a human rather than looping infinitely.
            

          


          

            
2. What the Harness Controls (mock-tools.mjs & observations.mjs)

            

              The harness controls event sequencing, state serialization (JSON.parse(JSON.stringify(state))), tool injection, and post-step invariant verification (verifying that no notification is ever sent without matching prior human approval and that attempts ≤ 2).
            

          


          

            
3. Where MCP / Tool Adapters Fit

            

              In production MOSU, tools.readProtocol and tools.notify sit behind an MCP Server / Tool Adapter boundary. Even if an AI agent proposes a tool call, the deterministic workflow engine and tool adapter enforce schema validation, approvedActionId === action.id authorization, and idempotency-key attachment before any external request leaves the boundary.
